# DOM → Figma 导出核心问题汇总

> 本文档记录 dom-to-json（生产端）与 mybricks-figma（消费端）在 DOM → Figma 转化链路中已发现的核心问题，以及每类问题背后的根本原因，作为长远迭代的参考指南。

---

## 一、根本性矛盾：CSS 的表达力 > Figma 节点模型

这是所有问题的终极来源。CSS 是一套图灵完备的声明式样式系统，而 Figma 的节点模型是一套**有限的设计原语**。两者之间存在无法完全映射的结构性差距：

| CSS 概念 | Figma 对应能力 | 差距 |
|---------|--------------|------|
| `display: flex` + `align-items` | Auto Layout + `counterAxisAlignItems` | `baseline` 等部分值需特殊处理 |
| `border` 在任意元素上 | 只有 FrameNode / RectangleNode 支持 strokes | TextNode 不支持边框 |
| `::before` / `::after` 伪元素 | 无对应节点，需估算位置手工生成 | 位置只能近似，不能精确 |
| `background-color` 在伪元素上 | 需生成 RectangleNode 填充 | 原先未支持，只处理了 border 类伪元素 |
| CSS 变量 `var(--xxx)` | 纯静态颜色值 | 变量在运行时解析，声明层拿到的是字符串 |
| `position: absolute` 与 Auto Layout 混用 | Auto Layout 内只能 `layoutPositioning: ABSOLUTE` | 负 margin、百分比定位均无法精确还原 |

**核心认知**：这套系统的本质是**有损转换**，永远存在表达力差距。每一个 bug 都是在某个具体场景下，转换逻辑选择了错误的"损"的方式。

## 二、已发现的具体问题与根因

### 问题 1：CSS 变量颜色 → 导出透明色

**现象**：tab 文字（如"城市店铺管理"）导出后变透明。

**根因**：生产端 `buildInlineTextStyle` 读取 `color` 时，拿到的是 CSS 声明层的原始值 `var(--color-primary, #1677ff)`，直接传给消费端；消费端 `parseColorWithOpacity` 遇到 `var(` 开头的字符串，无法解析，返回 `opacity: 0`。

**本质**：生产端读取样式时 **优先声明层（cssRuleMap）再 computed** 的策略，在 CSS 变量场景下会拿到未解析的变量字符串，而不是真实色值。`getComputedStyle` 才是浏览器计算后的真实值。

**修复方向**：声明层拿到 `var(` 时，自动降级到 `getComputedStyle`。（已修复 `buildInlineTextStyle` 和 `buildStyleJSON` 两处。）

**潜在同类问题**：任何通过声明层读取的属性，凡是值中含有 CSS 变量的，都有同样风险。背景色、边框色已有降级处理；其他属性（如 `font-size: var(--size-sm)`、`gap: var(--spacing-md)` 等数值属性）若使用变量，同样会在声明层拿到字符串，`parseFloat` 返回 `NaN` 后被静默忽略——目前因为这类场景少见而未暴露，但隐患存在。

### 问题 2：`background-color` 类图形伪元素被忽略

**现象**：`.tabItem.active::after`（蓝色下划线，仅靠 `background-color` 实现）不导出。

**根因**：`getPseudoShapeNode` 只处理"有 `border` 的"图形伪元素，`!hasBorder` 时直接 `return null`，背景色类伪元素被整体跳过。

**本质**：早期实现只考虑了分割线（border 型）伪元素场景，未考虑 Tabs 下划线（background 型）这类同样常见的场景。伪元素能表达的视觉形态有：文字内容（`getPseudoTextNode`）、border 分割线、background 色块——三种形态需要分别识别。

**修复方向**：检测 `backgroundColor` 是否非透明，若有则生成矩形节点；同时补充 `borderRadius` 读取。（已修复。）

---

### 问题 3：`<input>` 节点被判为 `text` 类型导致边框丢失

**现象**：输入框的边框线在 Figma 中消失。

**根因**：`inferNodeType` 把所有文本类 `<input>` 强制判为 `type: "text"`（注释写"防止因 padding/background 被误判为 frame"）。消费端 `buildText` 创建的是 Figma `TextNode`，而 TextNode **不支持 `strokes`**，`strokeWeight/strokeColor/borderRadius` 字段被静默丢弃。

**本质**：这是 **HTML 语义元素 → JSON 类型 → Figma 节点类型** 映射链上的错误选择。`<input>` 在视觉上是一个"有边框的容器 + 里面有文字"，对应的是 Frame（外壳）+ Text（占位符），而不是纯 TextNode。

当时把 `input` 判为 `text` 是因为担心 padding/background 触发 frame 判断，但这个担心方向反了——真正的问题是 TextNode 无法承载边框，应该判为 frame。

**修复方向**：`input/textarea` 改为 `frame`，在 frame 内生成一个子 text 节点展示 placeholder/value。（已修复。）

**潜在同类问题**：任何"叶子节点有 `border`"的 HTML 元素（如带 `border` 的 `<span>`、`<label>`、`<a>` 等），若被 `inferNodeType` 判为 `text`，边框和圆角都会丢失。当前 `inferNodeType` 只用 background/padding/radius 作为"升级为 frame"的条件，**漏掉了 `border-width > 0` 这个判断**，这是一个系统性的遗漏。

### 问题 4：`align-items: baseline` 映射为 `MIN`（顶对齐）

**现象**："店铺列表（共7条）"中大小字不基线对齐，而是顶对齐。

**根因**：生产端 `buildStyleJSON` 中的 alignMap 把 `baseline` 映射到 `'MIN'`（顶对齐）。

**本质**：Figma 的 Auto Layout 从某版本起**支持 `BASELINE` 对齐**（`counterAxisAlignItems: 'BASELINE'`），但 alignMap 是在 Figma 不支持时写的，直接用 `MIN` 降级，后来 Figma 补充了 `BASELINE` 支持，但映射表没有同步更新。

**修复方向**：`alignMap` 中 `baseline` → `'BASELINE'`。消费端 `types.ts` 已声明该值，`applyAutoLayout` 直接透传，无需改消费端。（已修复。）

---

### 问题 5：`<textarea>` placeholder 在 Figma 中垂直居中而非左上角

**现象**：多行文本输入框（`<textarea>`）的 placeholder 文字导出到 Figma 后显示在垂直居中位置，而不是左上角。

**根因**：antd 的 `ant-input-affix-wrapper` 是一个 `display: flex; align-items: center` 的横向容器，用来并排放置 textarea 和右侧的计数器（`ant-input-suffix`）。这个容器的 `counterAxisAlignItems: CENTER` 会把 `textarea` frame 整体拉到垂直居中。

最初的修复（只改 `singleLine: false` 和 `textAlignVertical: 'TOP'`）只改了 textarea 内部文字的对齐，但没有解决 textarea **自身 frame** 被父容器垂直居中的问题，因此 placeholder 依然偏下。

同时，最初把 placeholder 子节点改为 `positionType: 'absolute'` 时，对单行 input 也加了绝对定位，导致单行 input 的 placeholder 脱离了父 frame 的 Auto Layout，不再垂直居中——引入了副作用。

**本质**：`input` 和 `textarea` 对 placeholder 的定位需求截然不同：
- **单行 `input`**：希望 placeholder 由父 frame 的 Auto Layout 垂直居中，**不应该用绝对定位**
- **多行 `textarea`**：希望 placeholder 固定在左上角，**需要绝对定位**，且 textarea 自身 frame 需 `alignSelf: MIN` 覆盖父容器的垂直居中

**修复方向**（已修复）：
1. `textarea` 的 placeholder 子节点设 `positionType: 'absolute'`，使用明确的 `x/y/width/height`，`textAlignVertical: 'TOP'`
2. `textarea` 自身 frame 加 `alignSelf: 'MIN'`，覆盖父容器的 `counterAxisAlignItems: CENTER`
3. 单行 `input` 的 placeholder 子节点**不设** `positionType`，走父 frame Auto Layout，`textAlignVertical: 'CENTER'` 正常生效
4. 消费端 `layout.ts` 新增 `alignSelf` → `layoutAlign` 的处理；`types.ts` 补充类型声明

**迭代经验**：修复 textarea 定位问题时，要同时考虑 input 和 textarea 两种场景的差异，绝对定位和 Auto Layout 不能混用，否则会互相干扰。

### 问题 6：Frame 边框某些边（如左边）在 Figma 中消失

**现象**：`ant-list bordered` 卡片导出到 Figma 后，四周边框中左边消失，上下右三边正常。

**根因**：Figma Frame 节点的 `strokeAlign` 默认值是 `INSIDE`（向内描边）。当 Frame 内部有 Auto Layout 子节点填满宽度，或子节点宽度接近父节点宽度（padding 为 0）时，内侧的 stroke 会被子节点的背景/填充覆盖，导致视觉上某些边（通常是左/右）消失。

**本质**：CSS 的 `border` 是在盒模型外层绘制，不受内容影响；而 Figma 的 `strokeAlign: INSIDE` 是向内绘制，会被内容层覆盖。两者的渲染模型不同，直接映射时丢失了这个差异的处理。

**修复方向**（已修复）：在消费端 `applyStrokes`（`style.ts`）里，当没有显式指定 `strokeAlign` 时，有描边的节点统一设为 `strokeAlign: OUTSIDE`，边框画在节点外侧，不受内部子节点遮挡，四边均可见。

**潜在影响**：`strokeAlign: OUTSIDE` 会让边框向外扩展，导致节点视觉尺寸比实际 frame 尺寸大 `strokeWeight` 个像素。与 CSS 的 `box-sizing: border-box`（border 包含在宽高内）也不完全一致。如追求像素精度，正确解法是在生产端将 frame 尺寸减去 border 宽度，或在消费端将 padding 增加对应值来补偿——目前暂时接受这个视觉偏差，优先保证边框可见。

### 问题 7：flex-wrap 容器子项的 `margin-bottom` 行间距在 Figma 中消失

**现象**：搜索栏（两行表单项 + 按钮行）在 Figma 中两行紧贴，没有行间距。

**根因**：双重问题叠加：
1. 子节点 `searchItem` 的 CSS `margin-bottom: var(--spacing-base, 16px)` 中含有 CSS 变量，声明层读到的是字符串 `var(--spacing-base, 16px)`，`parseFloat` 返回 NaN，`marginBottom` 没有写入 JSON——这是**系统性问题 B 的数值属性版本**（之前只修了颜色类属性的变量降级）。
2. 即使 `marginBottom` 被正确读取，Figma 的 Auto Layout Wrap 模式下子节点的 `margin` 不会自动转化为行间距，需要设置**父容器**的 `counterAxisSpacing`。

**本质**：
- CSS 变量用于间距值（`margin`、`gap`、`padding` 等）和颜色一样普遍，但之前只对颜色属性做了 `var()` 检测降级，数值属性同样需要。
- CSS 的 flex-wrap 行间距可以用 `row-gap` 或子项 `margin-bottom` 两种方式实现，但 Figma 只有 `counterAxisSpacing`（父容器属性），无法通过子节点 margin 来实现行间距。需要生产端在 walk 阶段做转换。

**修复方向**（已修复）：
1. `buildStyleJSON` 中 margin 读取增加 CSS 变量降级：若声明层值含 `var(` 或 `calc(`，降级到 `computed`
2. walk 阶段：当父容器是 `layoutWrap: WRAP` 且没有 `counterAxisSpacing` 时，从第一个子节点的 `marginBottom` 推断，赋给父容器的 `counterAxisSpacing`

**潜在同类问题**：`gap`、`padding`、`font-size` 等所有数值类 CSS 属性，若使用 CSS 变量均存在同样风险。应封装统一的 `resolveStyleValue()` 函数统一处理，而非在每处零散修补。

### 问题 7（补充调试经过）：flex-wrap 子节点 `marginBottom` 被提前清除

**完整根因**（调试后修正）：

问题分为两层：

**第一层**：`margin-bottom: var(--spacing-base, 16px)` 中 CSS 变量导致声明层读到字符串，`parseFloat` 返回 NaN，marginBottom 未写入 JSON。已通过变量降级到 computed 修复（`resolved mB: 16` 确认正确）。

**第二层（真正拦截点）**：父节点（`searchFlex`，WRAP 容器）在处理子节点间距时，`ensureItemSpacingFromPositions` 推断出 `itemSpacing: 24`（横向间距），进入"统一清理子节点 margin"的逻辑（原意是"间距已经用 itemSpacing 表达，子节点 margin 不需要了"）。此时子节点的 `marginBottom: 16` 被**提前删除**。WRAP 推断逻辑（`counterAxisSpacing` 赋值）安排在清理之**后**执行，因此读到的全是 `undefined`，永远推断不出行间距。

**核心误区**：清理子节点 margin 的逻辑假设"所有 margin 都已经被 itemSpacing 覆盖"，但在 WRAP 容器中，`marginRight/Left` 对应横向间距（itemSpacing），而 `marginBottom` 对应行间距（counterAxisSpacing）——它们是**两个不同轴的属性**，不能一刀切清除。

**修复方向**（已修复）：在执行子节点 margin 清理**之前**，先检查父容器是否 `layoutWrap: WRAP`，若是则先提取子节点 `marginBottom` 赋给父容器的 `counterAxisSpacing`，再执行清理。两处 walk 函数均已修复，并保留兜底逻辑。

### 问题 7（调试过程完整记录）

**三层拦截——每次定位到一层，修了之后发现还有下一层：**

| 层 | 位置 | 现象 | 原因 |
|----|------|------|------|
| 第一层 | `buildStyleJSON` margin 读取 | `marginBottom` 未写入 JSON | `margin-bottom: var(--spacing-base, 16px)` 声明层读到变量字符串，`parseFloat` NaN |

### 问题 8：`ant-radio-button-wrapper` 选中态蓝色边框被相邻节点覆盖，`::before` 竖线位置错乱

**现象**：素材上传页面"图片/视频"tab 切换组件导出后：
1. 选中的"图片" tab 蓝色边框消失（被"视频" wrapper 的白色背景压住）
2. 两个 tab 之间的竖线缺失，且"视频"右侧多出一条竖线

**根因分析**：

**蓝线被覆盖**：DOM 中 `ant-radio-button-wrapper-checked` 的 `z-index` 比相邻 wrapper 高（蓝色边框需覆盖邻居白底）。但 Figma Auto Layout 中子节点层叠顺序由 `children` 数组下标决定——selected wrapper 排在前面，层级反而更低，导致蓝色边框被后面 wrapper 的白色 fill 覆盖。

**竖线错乱**：每个 `ant-radio-button-wrapper` 有一个 `::before` 伪元素（宽 1px 的绝对定位矩形，CSS 实现两 wrapper 紧贴时的分割线）。导出时 `getPseudoShapeNode` 计算坐标相对 host 元素，`x=-1`，在 Figma 中与左侧 wrapper 重叠，视觉位置错误，形成"右侧多出一条线"的假象。

**解决方案**：

在 `dom-to-json.js` 两处 walk 函数的子节点汇总阶段，识别 `ant-radio-group` 容器后：
1. **过滤 `pseudo-before`**：删除每个 `ant-radio-button-wrapper` 子节点中 `name === 'pseudo-before'` 的绝对定位子节点。CSS 竖线在 Figma 里无法精确还原，且 Figma 中两个 wrapper 的边框自然相邻，视觉上不需要这条线。
2. **不加 gap**：曾尝试 `itemSpacing = 1` 让两 wrapper 间保留 1px 间距使蓝线可见，但会在 Figma 中产生肉眼可见的间隔，最终去掉。蓝线覆盖问题通过接受"选中 wrapper 的右侧边框与邻居重叠"的方式处理——实际上去掉伪元素后，两 wrapper 各自边框相接，蓝线左边和底部已经足够表达选中态。

**修改文件**：`dom-to-json.js` 两处 walk（walk1 约第 801 行，walk2 约第 1327 行），新增：
```javascript
if (nodeJson.className && nodeJson.className.indexOf('ant-radio-group') !== -1) {
  for (var _rgi = 0; _rgi < childNodesList.length; _rgi++) {
    var _rgChild = childNodesList[_rgi];
    if (_rgChild && _rgChild.children) {
      _rgChild.children = _rgChild.children.filter(function(c) { return c.name !== 'pseudo-before'; });
    }
  }
}
```

**教训**：CSS 中靠 `z-index` 实现视觉层叠的组件（如 antd radio-button），在 Figma Auto Layout 中无法通过简单重排 `children` 还原，因为 `children` 顺序同时决定视觉位置。`::before` 伪元素作为"结构性装饰"（分割线）在 Figma 中没有合适的对应方式，过滤比保留更干净。

### 问题 9：`margin: 0 auto` 水平居中子节点在 Figma 中未居中

**现象**：商家中心页面"创建店铺 → 店铺装修 → 上传资质"步骤条（stepWrapper）在浏览器中水平居中，导出到 Figma 后贴左显示。

**根因分析（多层排查）**：

**第一层**：生产端 `buildStyleJSON` 尝试读取 `margin-left` / `margin-right` 的原始声明值来检测 `auto`，但 `.stepWrapper` 的样式为 `margin: var(--spacing-lg) auto`，声明层（cssRuleMap）在 Shadow DOM 场景下拿到的是 `undefined`，无法检测到 `'auto'`。

**第二层**：改用几何检测法——若子节点的 `x ≈ (parentWidth - childWidth) / 2`（误差 < 2px），认为是水平居中，设置 `alignSelf: 'CENTER'`。日志确认：`cX=185, expected=184.74`，检测成功。

**第三层**：消费端（VibeUI `layout.ts`）尝试 `node.layoutAlign = 'CENTER'`，日志显示 `before=INHERIT after=INHERIT error=none`——Figma Plugin API **静默忽略**了 CENTER 值，无报错，但设置无效。

**根本原因**：Figma Plugin API 中，当子节点 `layoutSizingHorizontal = 'FIXED'` 时，`layoutAlign` 只能为 `INHERIT` 或 `STRETCH`，设置 `CENTER/MIN/MAX` 会被静默忽略。这是 Figma 的 API 约束，无法绕过。

**隐患**：即使 VibeUI 在 fallback 中调用 `parentNode.counterAxisAlignItems = 'CENTER'`，由于 `applyLayoutAndSize` 会对父容器调用两次，第二次调用会从 JSON 原始值（`MIN`）把 `counterAxisAlignItems` 覆盖回去，导致 fallback 无效。

**最终修复方案**（`dom-to-json.js` 两处 walk）：

几何检测成功后，在 **JSON 生产阶段**直接将父容器的 `counterAxisAlignItems` 改为 `'CENTER'`，而不是依赖 VibeUI fallback。这样 VibeUI 两次 `applyLayoutAndSize` 都从 JSON 读到 CENTER，不会被覆盖。

**安全检查**：仅当所有其他非绝对定位兄弟节点均为全宽（`parentWidth - siblingWidth ≤ 10px`）时才修改父容器对齐方式，避免存在其他窄宽度兄弟节点时被错误居中。

```javascript
// 检测到居中子节点后：
_mcs1.style.alignSelf = 'CENTER';
var _allSibsFullWidth = true;
for (var _si = 0; _si < childNodesList.length; _si++) {
  if (_si === _maci) continue;
  var _sib = childNodesList[_si];
  if (!_sib || !_sib.style || _sib.style.positionType === 'absolute') continue;
  if (_sib.style.width != null && _pW - _sib.style.width > 10) {
    _allSibsFullWidth = false; break;
  }
}
if (_allSibsFullWidth) {
  nodeJson.style.counterAxisAlignItems = 'CENTER';
}
```

**修改文件**：
- `dom-to-json.js`：两处 walk 的 VERTICAL 布局检测块（walk1 约第 877 行，walk2 约第 1484 行）

**教训**：
1. Figma `layoutAlign = 'CENTER'` 在 `layoutSizingHorizontal = 'FIXED'` 时静默失效——这是 Figma API 约束，需要换思路改父容器。
2. VibeUI 的 fallback 逻辑会被 `applyLayoutAndSize` 的第二次调用覆盖，必须在 JSON 生产端就写入正确值，不能依赖消费端 fallback。
3. 修改 `counterAxisAlignItems` 会影响所有子节点，务必做兄弟节点全宽安全检查。

## 三、两大系统性问题（长远迭代指南）

### 系统性问题 A：inferNodeType 的"类型判断"不完整

`inferNodeType` 决定一个 DOM 元素映射为哪种 JSON 类型（text/frame/group/image/component），这是整条链路最关键的判断。目前的判断逻辑存在几个遗漏：

1. **有 `border` 的叶子节点仍可能被判为 `text`**：应在升级为 frame 的条件里加入 `border-width > 0`
2. **`input/textarea` 原来强制判为 `text`**：已修复，但背后的原则需要明确——**凡是有视觉外壳（边框/背景/圆角）的 HTML 表单元素，都应该是 frame，而非 text**
3. **`<select>` 等其他表单元素**：同样需要检查是否有类似问题

**迭代原则**：`type: "text"` 应只用于"纯文字展示节点"，没有任何边框、背景（非透明）和视觉外壳的情况。凡是兼有视觉容器属性（fills/strokes/borderRadius）的叶子节点，统一判为 `frame`，文字内容作为子节点。

---

### 系统性问题 B：声明层（cssRuleMap）vs 计算值（getComputedStyle）的优先级策略

**当前策略**：优先 cssRuleMap 声明层，没有再用 computed。

**设计初衷**：避免 Shadow DOM 内 getComputedStyle 无法拿到外部 antd CSS cascade 的问题。

**副作用**：声明层拿到的是"原始 CSS 文本"，包含：
- CSS 变量（`var(--xxx)`）：无法直接解析为颜色/数值
- CSS 函数（`calc(100% - 24px)`）：无法解析为像素值
- 相对单位（`em`/`rem`/`%`）：无法换算为像素

**正确的分层策略应该是**：
1. 先读声明层，检查值是否"可直接使用"（纯 hex/rgb/rgba/具体像素数值）
2. 若声明层的值含有 `var(`、`calc(`、`%`、`em`、`rem`，则**必须降级到 computed**
3. computed 的值永远是浏览器已计算好的最终值，是最可靠的来源

目前只有颜色类属性做了 `var(` 检测降级，其他属性（间距、字号等）若用了变量，仍然存在隐患。

**迭代原则**：封装一个统一的 `resolveStyleValue(declaredValue, computedValue)` 函数，集中处理"声明值是否可用"的判断，而不是在每个属性读取处零散地写降级逻辑。

---

## 四、整体架构建议

```
DOM (with CSS)
  │
  ▼
[dom-to-json.js] ← 生产端：有损转换，尽量保留视觉语义
  │  核心职责：
  │  1. inferNodeType：正确分类节点（text/frame/image/component）
  │  2. buildStyleJSON：正确读取样式（优先 computed，声明层辅助）
  │  3. 伪元素处理：text型 / border型 / background型 三种形态
  │
  ▼
[JSON 中间格式] ← 契约层：类型系统是生产/消费端的边界，改字段需两端同步
  │
  ▼
[mybricks-figma] ← 消费端：忠实还原 JSON，不做额外推断
  │  核心职责：
  │  1. buildNode 分发：按 type 调用正确 builder
  │  2. builder 职责：applyFills / applyStrokes / applyBorderRadius / applyEffects 全部调用
  │  3. Auto Layout：父有 layoutMode 时，子节点不能设 x/y（会触发 ABSOLUTE）
```

**一个检验标准**：每次新增一个 DOM 元素场景，问自己三个问题：
1. `inferNodeType` 会给它什么类型？这个类型在 Figma 中能否承载它的所有视觉属性？
2. 样式读取时，所有属性值是否都经过了"声明值可用性检查"？
3. 对应的消费端 builder 是否调用了全套 apply 函数（fills/strokes/borderRadius/effects）？

## 五、后续迭代建议

### 建议 1：封装 `resolveStyleValue(declared, computed)` 统一处理 CSS 变量/calc/相对单位

**现状**：每次发现一个属性有 CSS 变量问题，就在那个属性的读取处单独加 `var(` 检测降级。已零散修了 color、margin 等属性，但 `gap`、`padding`、`font-size`、`border-radius`、`letter-spacing` 等属性同样有隐患，只是当前业务场景未触发。

**建议**：封装一个统一函数：
```javascript
function resolveStyleValue(declared, computedVal) {
  if (!declared) return computedVal;
  var s = String(declared);
  if (s.indexOf('var(') >= 0 || s.indexOf('calc(') >= 0 || /\d+(em|rem|%)/.test(s)) {
    return computedVal;
  }
  return declared;
}
```
然后在 `buildStyleJSON` 中所有读取属性的地方统一用这个函数替换 `d(['xxx']) || computed.xxx` 模式，一次性消除所有隐患，而不是逐个打补丁。

---

### 建议 2：margin 语义分类处理，不能一刀切清除

**现状**：`margin` 在不同布局场景下语义不同：
- 普通 flex（非 wrap）：`marginRight/Bottom` → `itemSpacing`（主轴间距）
- flex-wrap 容器：`marginRight` → `itemSpacing`，`marginBottom` → `counterAxisSpacing`（行间距）
- 负 margin：降级为绝对定位，无法用 Auto Layout 还原

**建议**：在 walk 阶段对 margin 做语义分类，而不是统一清除：
1. 先判断父容器是否 WRAP
2. WRAP 时，横轴 margin（`marginRight`）→ itemSpacing，纵轴 margin（`marginBottom`）→ counterAxisSpacing
3. 非 WRAP 时，主轴 margin → itemSpacing，交叉轴 margin 保留或清除
4. 任何轴向有负 margin 才降级绝对定位

---

### 建议 3：`inferNodeType` 补全"有 border 的叶子节点"升级规则

**现状**：`inferNodeType` 的"升级为 frame"条件是：有背景色、有 padding、有 borderRadius。**漏掉了 `border-width > 0`**。

**建议**：在升级条件中补充：
```javascript
var hasBorder = px(computed.borderTopWidth) > 0 || px(computed.borderRightWidth) > 0 ||
                px(computed.borderBottomWidth) > 0 || px(computed.borderLeftWidth) > 0;
if (hasBorder) return 'frame';
```
这样凡是有 border 的叶子节点都会被正确分类为 frame，避免 TextNode 丢失边框。

---

### 建议 4：strokeAlign 问题的根本解法

**现状**：用 `strokeAlign: OUTSIDE` 作为兜底，避免边框被子节点覆盖。这会使节点视觉宽高比 frame 尺寸大 `strokeWeight` 像素，与 CSS `box-sizing: border-box` 不一致。

**建议**：正确做法是在生产端检测到有 border 时，自动将 frame 的 `width/height` 减去 `borderWidth`（border-box → content-box 转换），或将 `padding` 增加对应值以补偿。或者在消费端设 `strokeAlign: CENTER`（Figma 默认值），同时将 padding 增加 `strokeWeight / 2` 以保持视觉一致性。

---

### 建议 5：建立端到端测试用例库

**现状**：每次修复都依赖人工视觉比对（截图对比 DOM 和 Figma）。修复 input border 时引入了 textarea placeholder 问题，修复 textarea 时又影响了 input 垂直居中——**回归测试成本高**。

**建议**：建立一个包含典型 UI 模式的 HTML 测试文件，每种模式对应一个预期 JSON 片段，导出后自动 diff JSON 关键字段（strokeColor、counterAxisSpacing、textAlignVertical 等）。至少覆盖：
- 单行 input（有边框、placeholder 垂直居中）
- 多行 textarea（有边框、placeholder 左上角）
- flex-wrap 表单行（有行间距）
- CSS 变量颜色（不透明）
- 带 border 的容器（四边完整）
- 绝对定位子节点（在父容器顶层）
- 伪元素（::after 背景色）

---

### TODO 1：将 margin 处理集中到一个专用函数

**现状混乱点**：
- `applyUniformMarginAsGap`：清除子节点 margin，同时叠加到 `itemSpacing`
- `ensureItemSpacingFromPositions`：从坐标反推 `itemSpacing`

顺序固定、职责单一，不再散落在多处。
